# epoll 修正

这台手机的 epoll 有两处与 Linux 不同。HiSH 在 Linux 程序（musl 和 glibc）的预加载库里补上：代码在 `linux/epoll.c`，记账逻辑在 `hish_epoll_core.h`。测量和证据见 [验收](verification.md)。

## 一次性通知不起作用

`EPOLLONESHOT` 的意思是：事件送出一次之后，这个登记自动停用，直到程序用 `EPOLL_CTL_MOD` 重新登记。这台手机的内核忽略这个标志：管道、套接字、eventfd 上的一次性登记每次等待都再报一遍；`EPOLLET`（边沿触发）和普通电平触发与 Linux 一致。

Bun 第一次碰 `process.stdout` 或 `process.stderr`（管道，或 HiSH 的终端，它对 Linux 程序是一个套接字）时，为它的副本登记“可写、一次性”。描述符永远可写，于是每次 `epoll_pwait` 都立即返回，事件循环从不睡眠：每个碰过标准输出的线程占满一个核心。opencode 界面的主线程和后台线程各一个，空闲约 200%。输出到普通文件的程序不受影响，因为 `epoll_ctl` 对普通文件返回 EPERM。

### 做法

- 程序用 `EPOLLONESHOT` 登记时，告诉内核的是普通电平触发的登记（去掉该标志），同时在表里记一笔“已装填”。
- `epoll_wait` 返回后，对返回事件里的每个已装填的一次性登记，用 `EPOLL_CTL_DEL` 把内核里的登记删掉，表里改成“已触发”。从外面看，这与 Linux 的一次性相同：描述符保持安静。
- 程序再用 `EPOLL_CTL_MOD` 登记（这是它重新装填的办法）：对已触发的登记，内核里已经没有了，所以改成 `EPOLL_CTL_ADD`；如果内核其实还有（`EEXIST`），就改回 `MOD`。`ADD` 和 `MOD` 都会重新检查描述符现状，装填时已经就绪的数据不会丢。
- `EPOLL_CTL_DEL` 一个已触发的登记直接返回成功，不碰内核，与 Linux 对已停用登记的行为一致。
- 事件只带用户数据，不带描述符号，所以同一个 epoll 集里，两个已装填的一次性登记不能有相同的用户数据；后到的那个不追踪，原样交给内核（旧行为，可能空转）。表满（每进程 2048 项）时同样不追踪。
- 创建新的 epoll 描述符时，清掉表里属于这个号码的旧记录。关闭描述符不会通知本层；旧记录在同一描述符号码的下一次 `ADD`、`DEL` 时被覆盖或清除。

### 何时启用

第一次出现一次性登记时，库自测内核：建一个管道和 epoll，把写端用 `EPOLLOUT|EPOLLONESHOT` 登记，不等待地问两次；第二次仍有事件就说明内核忽略了标志，启用模拟。内核以后修好这个问题，库自动不介入。结果缓存在进程里；自测本身做不成（比如描述符用完）就下次再试，其间不介入。

环境变量：`HISH_EPOLL=0` 完全关闭模拟（排查用），`HISH_EPOLL=1` 不自测、强制开启。

### 覆盖的入口

- 函数：`epoll_create`、`epoll_create1`、`epoll_ctl`、`epoll_pwait`、`epoll_wait`。`epoll_pwait` 仍交给 C 库自己的实现（保留取消点和重启行为），本库只在返回后做记账。
- 经 `syscall()` 的调用（系统调用号 20、21、22、441）：Bun 和 Rust 的 libc 库登记事件走这条路。`linux/links.c` 拥有 `syscall()`，先问 `linux/epoll.c`，不受 `HISH_LINKS` 影响。
- 直接用 `svc` 指令发起的 epoll 调用绕过本层。Bun 1.4.4 的 `epoll_ctl` 和 `epoll_pwait` 都不是内联 `svc`（`bun_epoll_pwait2` 里有三处内联 `epoll_pwait2`，本机不走）。

### 与 Linux 的差别

- 对已触发的一次性登记再做 `ADD` 会成功，Linux 返回 `EEXIST`。这是为了让复用描述符号码的程序（旧登记的描述符已关闭）能继续工作。
- 事件送出到本层删除内核登记之间有一个很短的窗口；窗口里到达的新数据由下一次装填重新检查，不会丢。但多个线程同时等待同一个 epoll 集时，这个窗口里别的线程可能拿到同一个事件。Bun 每个线程用自己的 epoll 集。
- 持有内核登记的描述符被 `dup` 后关闭原号码，内核登记会留着，本层删不掉（号码已关闭）。这在没有模拟的旧行为里同样存在。
- 表用一把自旋锁保护；信号处理函数里调用 epoll 且恰好打断持锁线程会死锁，实际程序不这样做。

## epoll_pwait2 不再杀进程

应用的 seccomp 过滤对系统调用 441（`epoll_pwait2`）直接发信号 31（SIGSYS）杀死调用者，实测如此。Bun 靠内核版本检查避开它；任何直接调用 glibc 的 `epoll_pwait2` 或 `syscall(441)` 的程序会被杀。库提供 `epoll_pwait2`，并把 `syscall(441)` 转成 `epoll_pwait`，超时向上取整到整毫秒，使亚毫秒的等待不变成忙等。这一部分始终开启，`HISH_EPOLL` 不影响它。

## 测试

- 主机：`node --test tests/epoll-emulation.cjs`。真实记账代码跑在两个模型内核上：一个按 Linux 行为（一次性登记触发后停用），一个按这台手机（忽略标志）。43 个单项加一次 120000 步的随机游走，每一步的应答和返回事件都必须与 Linux 模型一致；对记账故意做两处破坏，测试都能抓到。同一文件用严格告警为 musl 和 glibc 编译 `epoll.c`、`links.c`、设备检查程序，并检查设计约束。
- 真机：见 [测试](testing.md) 的“epoll 的设备检查”。
