# 通用兼容层与包管理器重构方案

状态：**设计方案，尚未实施**。基线为 2026-10-30 的工作区实现与同日 debug HAP 真机验证；工作区包含尚未提交的改动。本文约定目标、实现顺序及验收方式，不表示这些目标已经可用。

本文与[执行兼容层现状](elf-runtime.md)、[包管理器现状](packages.md)、[软件交付边界](distribution.md)和[执行纪律](safety.md)配合阅读。发生冲突时，现状文档描述当前行为，本文描述拟实施的行为；实施后应同步更新现状文档。

## 1. 目标和边界

目标是在现有应用权限和宿主系统允许的范围内，让更多同架构 Linux 命令行程序通过同一套机制直接安装和运行，减少使用者为单个程序寻找补丁的需要。兼容处理按 **ELF、运行库、文件系统、进程及系统调用的语义**组织，而不是按应用名组织。

包管理方面：

1. 普通仓库包按仓库元数据解析，不设置软件包或依赖白名单。
2. 确需修改源码才能适应平台、且适配方案经过验证的软件，可以将适配构建及其必要运行依赖随 HAP 附送，由数据描述其来源和依赖。
3. 随 HAP 附送的包属于应用管理的本地来源。`pkg` 可以按需安装其副本，但不能通过任何包操作将其更新或替换为远程版本；这类包只随 HAP 更新及应用自身的迁移流程变化。
4. 普通远程包继续按可信仓库元数据发现和更新。兼容性报告与是否允许安装分开。
5. 不按应用名、固定版本、下载链接或某一设备型号在运行时写分支。能根据文件、包元数据和宿主能力可靠检测的，由通用机制检测。

“所有程序都无缝运行”是努力方向，不是当前可以保证的结果。宿主内核、应用安全域、系统调用策略、架构、硬件及真实权限会限制用户态实现。不能通过伪造成功返回、放宽系统权限、绕过设备安全机制或为某个程序提供空壳来制造兼容结果。需要特权操作、特定硬件、内核模块、完整 init 或图形栈的软件，须逐项说明能力与验证结果。

这里的“禁止硬编码”指禁止把易变化的应用身份、来源、版本、路径和设备判断写成产品行为分支。ELF/系统调用 ABI 常量、受版本管理的数据格式、安全边界、受保护的信任根、资源上限及可复现构建所需的输入摘要仍然需要明确给出；不能用未经验证的动态数据替代信任根。默认配置及随 HAP 签名分发的清单是数据，不是程序包白名单；变更这些数据不能绕过来源验证。

## 2. 当前基线

| 部分 | 已有实现 | 对重构的影响 |
| --- | --- | --- |
| 公共执行路径 | HiSH 有 ELF 加载、musl/适配 glibc、exec 桥、部分进程和终端兼容。部分 libc 调用经过兼容入口；原始系统调用和静态程序不一定经过它。 | 可复用现有机制，但不能把某次应用通过等同于完整 Linux ABI。 |
| PRoot | 随包保存 PRoot 源码适配构建，`pkg install proot` 时复制出来；通过特定加载脚本与桥接程序启动来宾，PRoot 自身负责路径及系统调用跟踪。 | 加载协议和启动补丁目前是 PRoot 专项；通用映射、执行能力可以抽取，PRoot 协议适配仍有独立边界。 |
| 仓库 | Alpine v3.23 main/community aarch64，经 APK 工具解析、下载和验签；未设包名/依赖白名单。 | 延续 APK 的元数据和签名模型，避免自写一套与上游不一致的依赖语义。 |
| 特殊包 | `package_manager.cpp` 按 `bun`、`proot` 名称分支。Bun 下载固定的官方 npm 归档；PRoot 读取 HAP 内产物；依赖也有专门处理。 | 以通用来源和清单替换名称分支；Bun 目前并非随包附送。 |
| 更新 | `pkg upgrade` 重建请求集合；普通 Alpine 包重新解析，Bun/PRoot 重装当前 HAP 固定版本。 | 现有行为不等于完整的本地包保护：重建过程仍依赖名称分支，普通依赖仍可变化。 |
| 安装 | gzip/tar、大小上限、路径及签名检查；不运行安装脚本；文件链接转为副本，目录链接不支持。 | 安装成功不保证完整包语义。需要补齐能力或明确拒绝/报告不完整，不能把副本当成真实链接。 |
| 激活 | 通过临时目录和两次重命名切换代次，保留 previous；尚无断电持久性或运行中升级无缝保证。 | 需要更明确的事务、恢复及运行中代次引用模型。 |

2026-10-30 的已测范围包括：Bun 脚本、Worker、子进程、npm 安装和 PRoot 内执行；PRoot 的 musl rootfs 文件操作、shell、fork/exec，以及一个静态 BusyBox 场景。具体记录见[验收](verification.md)。这不是任意静态 ELF、glibc 发行版、其他设备、release 安全域或全部系统调用的证明。

关键现有入口：`feature/hish_main/src/main/cpp/{native_elf.cpp,linux/exec.c,exec_bridge.cpp,proot_loader.cpp,package_manager.cpp,package_archive.h}`；PRoot 补丁位于 `scripts/packages/proot-build.cjs` 和 `scripts/packages/proot/`；自举及当前固定来源位于 `scripts/packages/{prepare.cjs,bootstrap-lock.json,upstream.json,proot-lock.json}`。

## 3. 不变量

实现与测试必须始终满足以下合同：

- **N1 通用路由：** 程序路由取决于实际格式、ABI、清单及宿主能力；不能因程序名、路径尾缀、文件摘要或单个设备型号选择应用专用实现。运行目标必须是用户请求的真实文件。
- **N2 真实结果：** 错误必须保留可诊断的原因；不能将未实现的系统调用一律伪装为成功，不能将安装成功或版本输出称为功能验证。
- **N3 完整性：** 来源验证、架构/格式、归档路径、链接、文件冲突及资源限制对所有来源生效；不得为了兼容某个应用关闭这些检查。
- **N4 本地包不可被 pkg 更新：** 对已安装本地包，`update`、`upgrade`、安装/移除其他包、重算依赖、恢复或修复都不能改变其已安装版本和已记录的目标内容摘要；远程同名包、虚拟提供项、文件覆盖和依赖求解不能绕过这一规则。若无法保留，事务失败并保留旧代次。
- **N5 来源可追溯：** 清楚区分 HAP 内本地产物、官方仓库、其他远程源和旧状态未知来源；不把摘要一致描述为上游签名通过，也不把旧记录无依据地认定为可信。
- **N6 数据保留：** 不覆盖或删除 HOME、非包管理器管理的软件、用户自改配置、历史和用户数据。用户请求的包更新可创建新代次，但迁移、失败及崩溃恢复保留原代次；清理只针对确认无引用且属于管理器的内容。
- **N7 失败可回退：** 下载、验证、解包、依赖冲突及激活失败不能发布半成品；已经运行的进程不能因新代次切换而被删除所依赖的文件。
- **N8 不虚构能力：** 动态探测不能越权、不能改变系统策略；未测、拒绝和不支持分开记录。被禁用的能力不能因一次探针或一次失败被推断为所有设备的永久结论。
- **N9 边界明确：** PRoot 不提供内核 root，也不是安全沙箱。应用自身权限及系统策略仍然有效。

## 4. 目标架构

```text
用户命令 / 脚本 / 软件子进程
             │
     通用执行入口与代次选择
             │
  格式和 ABI 识别 + 宿主能力决策
             │
 ┌───────────┼──────────────────────┐
 │           │                      │
宿主原生执行  Linux ELF 加载/exec 桥   可用时的系统调用协调后端
 │           │                      │
 │       libc、进程、文件、终端          通用语义处理
 │                                  │
 └───────────┴──────────┬───────────┘
                        │
               应用权限内的宿主内核

pkg → 来源适配与验真 → 统一依赖求解 → 私有事务代次 → 执行入口
            ↑
      HAP 本地清单 / APK 仓库 / 其他明确配置的来源
```

图中的系统调用协调后端是**待验证的候选能力**，不是当前已实现的全覆盖拦截器。具体实现需以设备和安全域的证据选型；一个能力缺失不能使同一套程序改走未经验证的路径。

### 4.1 文件识别和执行选择

1. 按实际文件内容识别 ELF、脚本 shebang 或宿主可执行格式；校验架构、位宽、字节序、ELF 类型、段和解释器等。对脚本解析解释器和参数，保留标准错误语义；不能仅凭扩展名。
2. 对 ELF 分析 `PT_INTERP`、动态依赖及可用的 ABI 元信息，结合来源提供的可信包信息，选择明确支持的加载器和库集合。静态 ELF 没有 `PT_INTERP`，不能因此推断其所有系统调用可被兼容。解释器路径或名字的片段不是完整 ABI 证明；无法判断时报告未知，而非猜成 musl/glibc。
3. 允许使用已验证的宿主原生路径或 HiSH Linux 路径。选择依据是格式和能力，而不是应用名；不执行一次目标程序再根据副作用或退出码偷偷重跑另一条路径。
4. 从实际设备/运行环境取得架构、页大小、私有目录和可用资源；加载器和归档仍有明确的安全边界。若当前实现只支持特定页布局或架构，必须拒绝并说明，不能因为探测到了新页大小就假装支持。
5. 维持真实 `argv`、环境、工作目录、标准流、文件描述符、`CLOEXEC`、信号和进程生命周期语义；`/proc/self/exe` 等涉及内核真实身份的部分单独标明是否等价。

### 4.2 兼容层的组成

建议按稳定职责拆分，不要求一次性改名所有文件：

| 组件 | 职责 | 必须处理的接口/边界 |
| --- | --- | --- |
| 能力检测 | 探测与当前设备、系统版本、应用版本和安全域相关的可用操作。 | 区分 `supported`、`unsupported`、`denied`、`unknown`；轻量无副作用检查与显式运行的隔离实验分开；环境变化后失效。 |
| ELF/脚本入口 | 检查真实文件、ABI 和解释器，选择可用执行路径。 | PIE/非 PIE、动态/静态、加载段边界、参数环境、错误回传；未知格式不猜测。 |
| 映射和链接 | 共用 ELF 映射、运行库搜索和重定位基础设施。 | W^X、地址冲突、页对齐、TLS、符号版本、解释器和依赖定位；不同 libc 保留各自 ABI 实现。 |
| 进程与线程 | 实现已验证的 exec、spawn、fork、等待、信号及描述符语义。 | 多线程 exec、继承、竞争、退出状态；禁止将包装器上的成功视为底层完整语义。 |
| 文件和路径 | 承载私有代次、路径映射及可实现的链接语义。 | 相对路径、`openat`、符号链接、硬链接、目录链接、`readlink`、循环/逃逸及并发修改。 |
| 终端与设备 | 统一终端能力及对 `/dev`、`/proc` 的访问和报告。 | 真实 PTY 与当前回退通道分开，处理窗口、信号、作业控制，不承诺伪造设备。 |
| 系统调用后端 | 只有经过能力和语义验证的操作才做拦截/转换。 | 动态链接入口、静态程序直接 syscall、多线程、子进程、异常及性能均须分别验证。 |

把当前分散的通用代码逐步抽到上述边界，维持单一执行合同。不得在各组件中增加 `if (程序名 == …)` 的“兼容表”；发行包中的静态资源、shell applet 名称及格式定义不是应用兼容判断。

### 4.3 系统调用拦截选型与 PRoot 共存

`LD_PRELOAD`/libc 入口只能覆盖实际经过这些入口的调用，不能声称拦截静态程序或内联的原始 syscall。`ptrace` 可以跟踪线程及其系统调用，但需要处理每个线程、fork/clone/exec、信号和跟踪器所有权，且可能与应用自己的调试器、PRoot 冲突。seccomp 用户通知、其他内核机制是否可用必须实测；当前设备的历史实验未能启用该通知，不能将其列为默认能力。

实施前先比较以下路线：

1. **公共 libc/加载器路径：** 保留和完善，不宣称覆盖直接 syscall。
2. **单一协调器路线：** 在宿主允许且测试通过时，由一个协调器负责跟踪、线程生命周期和通用 syscall 处理；PRoot 以可组合的路径/加载协议适配参与。是否能与原版 PRoot 组合，需要原型证明。
3. **PRoot 自身跟踪路线：** 保留 PRoot 管理来宾的跟踪，提取与应用无关的映射和执行代码；在 PRoot 外运行的其他程序不因此自动获得同等拦截。

不得假设两个独立跟踪器可以同时无冲突地接管同一线程；如无法组合，明确选择一个所有者或报告冲突。先用真实静态/动态、多线程与嵌套场景证明正确性，再决定是否默认启用。若宿主拒绝或语义无法保持，返回可诊断错误，不尝试提权。

PRoot 特有的加载脚本解析可以保留为协议适配器；应与通用 ELF 映射、运行库发现、参数/环境和进程管理分离。判断是否需要 PRoot 协议应来自明确的调用/协议上下文，而不是被运行的应用名。修改后的 PRoot 与原版的差异、源码、补丁、构建方式、许可及来源要可追溯；仅在验证发现端口仍有必要时继续随包提供，不因“曾经打过补丁”永久固化方案。

### 4.4 能力探测原则

- 默认只做不改变用户数据及系统设置的轻量检测；需要创建文件、子进程、跟踪或执行测试程序的探测放在私有临时范围，并显式标明成本及副作用。禁止自动调整权限、设备设置或解锁设备。
- 按实际操作结果记录 errno、阶段和环境；例如 `EPERM`、`EACCES`、`ENOSYS`、`EOPNOTSUPP`、`SIGSYS` 不能混为一个原因。失败可能取决于参数、路径和安全域，不等于同类调用全部不可用。
- 缓存的能力记录应包含系统构建/架构、应用构建与安全域等可获得的环境标识；任何标识改变后重新验证。无可靠标识或条件改变时保守标记未知。探针成功只证明该探针场景。
- `pkg doctor` 默认展示来源、依赖、安装状态及可公开的能力结果，不因未知而拒绝普通包，也不自动执行任意包声明的脚本或联网探针。深度功能测试必须显式触发，并显示使用的输入与测试范围。

## 5. 来源、元数据和依赖模型

### 5.1 统一来源接口

定义与应用名无关的来源接口：读取索引/清单、查询候选版本、取得包元数据、获取内容、验证来源、声明来源类型和更新策略。不同协议各自实现适配器，但统一输出依赖求解所需的包身份、版本、架构、依赖/提供项、文件清单和内容摘要。

- **HAP 本地来源：** 清单和载荷随应用分发；清单从受应用包完整性保护的资源读取，包含构建产物摘要。复制到可写目录后的副本重新校验，不能信任用户可写的来源标记作为保护依据。本地来源不联网，来源身份及保护策略由已验证的 HAP 清单决定。
- **APK 仓库来源：** 读取配置的仓库索引，使用仓库信任根验证索引与包；架构和版本来自元数据。优先复用现有 APK/libapk 的依赖语义和成熟索引格式，而不是用简单的字符串比较重写求解器。[APK 包元数据](https://github.com/alpinelinux/apk-tools/blob/master/doc/apk-package.5.scd) 和 [仓库格式](https://github.com/alpinelinux/apk-tools/blob/master/doc/apk-repositories.5.scd)可作为实现依据。
- **其他远程来源：** 只有具备明确来源配置、元数据和验证规则的适配器才可接入。适配器协议可以是通用 npm 元数据或其他格式，但不能据此声称任意 npm 包都能作为系统程序安装。来源配置和允许的信任根需要受到保护，不能让远程索引自行扩大信任范围。

本地清单不是可安装应用白名单：它只定义 HAP 内提供和保护的包。普通软件能否查询/安装仍取决于已配置来源、元数据、完整性、架构与通用安装能力。

### 5.2 本地包清单合同

清单由构建流程从实际载荷生成，并以版本化格式保存；以下是需要表达的语义，不规定最终字段或文件名：

| 信息 | 用途 |
| --- | --- |
| 规范化包身份、版本、架构 | 求解、冲突判断和展示；支持来源格式的版本规则。 |
| 载荷位置、内容摘要、文件清单及权限 | 本地读取、重新校验、文件归属和冲突检测。 |
| 依赖、版本约束、虚拟提供项、冲突项 | 与远程包在同一求解问题中处理；包含真实 ABI/SONAME 要求。 |
| 更新所有权与可移除属性 | 标记为 HAP 管理；是否允许移除安装副本由声明及依赖决定。 |
| 原始项目、上游版本/修订、适配补丁、构建输入和许可 | 复现、审计及源码交付；不把适配版冒充上游原版。 |
| 清单/包格式版本 | 防止旧客户端错误解释新语义；未知必要字段或版本应拒绝事务。 |

实际包身份和来源映射可以存在声明式数据中；不能为它们添加 C++ 专用分支。版本、来源 URL 和摘要的变化应由可信元数据/构建产物带来，而不是修改运行时逻辑。构建时固定输入是为了复现和核验，不代表运行时应固定所有远程软件版本。

可优先评估将本地产物组织为 APK 兼容的本地索引和包，使 APK 求解器能同时处理本地与远程依赖。APK 文档支持本地仓库形式，但现有 HiSH 当前仅调用 APK 的 fetch/verify 等命令，**本地候选约束与求解器组合尚未实现或验证**。必须先证明特定 APK 版本能准确表达下述锁定、虚拟提供项及冲突；若不能，以明确的适配层提供等价约束并用测试对照上游语义，不自行声称已有支持。HAP 本地来源的信任基于应用分发完整性；若采用额外 APK 签名，应独立设计签名与公钥管理，不能在仓库或终端日志中放私钥。

### 5.3 本地包及其依赖

PRoot 作为当前候选本地适配产物：构建时将适配后的程序、必要元数据、源码和许可入口纳入 HAP；按需安装副本，不要求默认进入 PATH，也不随包附带 rootfs。为了真正实现离线安装，必须把它的必要运行依赖也包含在可信本地来源中，或采用经过验证的私有依赖打包方式；仅随包放主程序、仍需联网下载 talloc，不算离线自带。

依赖可通过包管理器正常共享，也可在验证 ABI、许可证和路径语义后作为私有依赖；最终方案由冲突与体积测试决定。若依赖本身作为 HAP 本地包分发，它同样受 N4 保护。其他远程包要求不兼容版本时，报告完整冲突，不得偷偷替换本地依赖或用不同 SONAME 的库冒充。自带依赖的安全更新需要新的 HAP。

对 Bun：当前使用未修改的官方 npm 二进制，尚不属于随包自带软件。建议改成由通用远程来源适配器按官方元数据发现版本和载荷，并以声明式映射表达其命令、架构及系统库依赖；不得在核心安装器里为 Bun 写分支。安装仍要求满足依赖和运行格式。过渡期间保留现有固定版本行为，直到新路径完成验证。若以后选择将 Bun 作为 HAP 本地包附送，则自动适用本地包不可由 `pkg` 更新的同一规则，而不是另加 Bun 特例。

对 npm 来源，要求 TLS 和主机名校验，并校验元数据提供的强完整性摘要；缺少必要摘要或不符合来源策略时失败。摘要与载荷来自同一未独立签名的元数据时，只证明二者一致，不能称为上游独立签名。若启用 npm 注册表签名，应验证签名和对应受信任密钥，并记录实际验证结果；不可把 Alpine APK 验签结果套用到 npm。[npm 元数据与完整性字段](https://github.com/npm/pacote#manifests)。

### 5.4 求解与冲突

以同一个事务快照加载请求集合、已安装状态、可信本地清单和远程索引。规范化身份、依赖、版本和虚拟 `provides` 后统一求解；本地已安装包及其内容为固定约束，远程包只能在该约束满足时选择。普通依赖可以更新，但必须同时满足本地包的版本与 ABI 约束；没有解时失败，展示导致冲突的依赖链。

HAP 清单中声明的本地**主包身份**保留给本地来源，即使尚未安装，同名远程候选也不能作为替换来源。虚拟提供项不自动成为全局禁止的名字；按照上游求解语义处理，但不能借别名替换已锁定的本地包。还要基于文件所有权检测不同包的相同路径、不同文件的覆盖和库查找顺序，防止通过文件冲突绕过包身份保护。除非包格式明确表达并经验证支持的替换规则能够满足本地保护，冲突就失败。

不要把 npm 的 semver、APK 的版本比较及本地格式混成一个未经定义的比较器。每种来源须明确版本语义及其如何映射到统一约束；不能可靠映射时拒绝跨来源解，而不是选择看起来“最新”的字符串。安装前固定完整解和每份内容摘要，避免索引在事务中途变化造成混装。

## 6. pkg 行为合同

| 命令 | 拟定行为 |
| --- | --- |
| `pkg search` / `pkg info` | 合并已配置来源的查询，展示来源、版本、架构及本地包是否受 HAP 管理；同名冲突不隐瞒。 |
| `pkg list` | 展示请求包与已安装依赖、版本、来源、安装/配置状态；旧状态未知也明确显示。 |
| `pkg update` | 只刷新可更新远程来源的索引，不改变已安装内容、本地清单或本地版本；离线时本地来源仍可查询。 |
| `pkg install NAME...` | 使用求解后的精确内容；本地包从已接受的 HAP 本地来源安装副本，不联网取同名远程包。若本地来源迁移未完成，不由此命令迁移或覆盖。 |
| `pkg upgrade` | 更新满足约束的普通远程包；对每个已安装本地包保留现有版本、内容及来源，显示跳过原因。不使用最新 HAP 载荷替换旧安装副本。 |
| `pkg remove NAME...` | 可移除允许移除的安装副本；不删除 HAP 中的产物。被其他包依赖或标为运行所必需时按通用依赖/声明规则报错。 |
| `pkg doctor` | 报告来源、完整性、依赖、能力及未配置事项；深度功能检查仅显式执行。 |

如果引入修复/重装命令，修复只能从可信的**同一版本、同一摘要**内容恢复已安装副本；当前 HAP 不再提供原内容时不得用新版本冒充修复。不能将本地包重新安装成另一个版本，不能借 `install`、`upgrade`、回滚或来源参数绕过保护。`pkg` 自身对运行时文件的约束不等于保护用户免于手工修改私有文件；手工修改应被校验发现并报告，不能在普通升级或安装其他包时静默覆盖。

## 7. 安装语义和安全边界

### 7.1 文件、链接与归档

归档检查覆盖路径规范化、绝对路径/`..`、设备文件、重复条目、链接循环、目标逃逸、权限和资源上限。路径操作要以事务根的目录描述符为边界，避免先检查字符串、后跟随被并发替换的路径；如果宿主不支持需要的原子路径解析能力，就使用经过验证的安全替代，无法保证时拒绝。Linux 路径查找相关语义见[内核文档](https://docs.kernel.org/filesystems/path-lookup.html)。

先探测在应用私有目录创建真实文件、硬链接、符号链接及目录链接的能力。能够保留真实语义时优先使用；不能时可研究基于元数据的路径转换，但只有在动态程序、静态程序、直接 syscall、`readlink` 和目录遍历等通路均有一致证据后才能称为支持。普通文件副本不能模拟链接身份、后续目标修改或目录链接；现有副本方案只能标记为受限实现，不能继续当作完整链接。

若某包需要尚不能正确表达的链接、文件类型或归档格式，默认停止事务并指出原因；不得静默装成“完整成功”。明确的受限安装模式如果将来提供，必须由用户选择并记录为不完整，不能作为默认的完整安装。现有大小限制应根据格式和可用资源重审，既避免无根据固定某个应用大小，也不能移除防止耗尽资源的上限。

### 7.2 安装脚本和触发器

当前跳过安装脚本/触发器；这会使部分包未配置完成。目标是按包格式的依赖顺序实现脚本和触发器，但不能假设 PRoot、路径前缀或预加载就提供了安全隔离，也不能声称事务能回滚网络请求、宿主设置或事务目录外的写入。

首版策略：检测到必须执行而尚不支持安全执行的脚本/触发器时，默认失败并解释；若以后提供显式的“跳过脚本”选项，应将状态标为未配置，不能伪称安装完整。脚本执行后端只有在真实验证了路径约束、可执行范围、外部写入及网络等副作用的控制能力，且能区分可回滚与不可回滚操作后才能启用；无法证明这些约束时保持失败。对服务启动、系统配置和真实 root 权限的请求不伪造成功。来源签名只能说明来源/完整性，不能自动证明脚本安全。

## 8. 事务、持久化和并发

使用不可变的已验证代次和独立的活动代次记录；以下是目标合同，不声称现有两次重命名已满足：

1. 加锁并检查恢复状态，读取一致的活动代次、世界集合、受保护本地清单和来源索引快照。
2. 在不改变活动代次的前提下求解，下载并验证精确内容，计算空间需求；针对本地包携带旧代次的**同版本、同摘要**文件，禁止因新 HAP 清单而替换。
3. 在新的私有代次中写入文件、所有权、来源、依赖、状态及校验记录；检查完整性、冲突和所需配置状态。已有用户数据不放进被整体替换的包目录。
4. 在已验证支持的文件系统上，使用可验证的原子活动记录切换；按需要同步数据、目录及事务日志。`fsync`、rename 等的可用性和崩溃保证须实测，不能仅因调用成功就宣称已证明断电安全。无法满足时拒绝宣称该级别保证。
5. 启动恢复时按记录判断未完成准备、已切换及不一致状态，选择最后可验证的完整代次；恢复不得联网升级或替换本地包。旧代次及原始日志保留到安全回收。

活动记录可采用普通文件和原子替换，不依赖宿主一定允许符号链接。执行入口/会话必须绑定明确的代次，运行中的进程和后代继续使用其代次；新会话或明确刷新后才使用新代次。不能让一个进程在升级前后混用旧可执行文件与新库。如何准确跟踪进程及子进程对代次的引用、处理崩溃和 PID 重用，需要实现和实测；引用不确定时保留旧代次，不强删。并发安装、更新、卸载和 HAP 迁移共用事务锁与版本检查；空间不足时提示，不能删除未知用途的用户文件来腾空间。

## 9. HAP 更新和旧数据迁移

`pkg` 与应用自身迁移是不同操作：只有安装新的 HAP 后，应用迁移器才可以按新 HAP 清单把**已安装**本地包迁移到新随包版本。迁移器使用同样的依赖求解、验证、事务和冲突检查；不调用 `pkg upgrade` 来绕过 N4。不因新 HAP 附带某包而自动为原本未安装的包创建安装副本。

应用应记录最后一次成功接受的 HAP 本地清单代次、清单摘要与安装状态。HAP 变化时由应用迁移器检查和提交新清单；清单不变时也要完成关联确认。迁移待完成或失败期间，`pkg` 只能查询状态，阻止会修改包状态的操作并说明原因，直到应用迁移成功；这包括先移除再安装、修复及重算依赖，避免将待迁移的新 HAP 载荷变相当作 `pkg` 升级。成功迁移后，未安装的本地包仍保持未安装，将来首次安装使用已接受的新清单。已安装包的旧代次与可信来源材料应按恢复需要保留；不满足原版本内容校验时不得伪造修复。

迁移前保留旧代次和记录，核对用户修改与来源；依赖无法满足、HAP 载荷损坏、空间不足或文件冲突时保留旧状态并报告。新运行时与旧代次不兼容时应明确报错，不承诺必然能继续运行。新 HAP 不再提供旧本地包时保留现有内容并标记来源状态，不能自动用远程同名包顶替。

从现有 `native/packages/root/.hish-package/{world,installed.tsv,metadata}` 导入时：

1. 只读旧记录，保存原始快照；`world` 是用户请求集合，`installed.tsv` 还包含依赖。先记录实际文件和可用来源证据，不能只按包名猜来源。
2. 已安装的旧 PRoot/Bun 可通过原有来源记录与可信载荷摘要逐项比对；旧文件已改动、摘要不可获得或来源无法证明时，标为 `legacy-unknown` 并保留原件。当前记录不保证具备每个文件的完整摘要，不能凭版本文本断言内容未变。
3. 未知来源或用户修改的文件不能被远程求解结果静默覆盖；先报告冲突。只有在来源和内容可验证、数据能完整映射时才生成新状态。
4. 完成新代次并验证后切换；任意阶段失败保持原安装可见。保留旧目录及用户 HOME；以后回收前再次确认所有权和运行引用。

迁移既要验证从当前实现升级，也要验证从空安装和多次 HAP 升级的情况；不能要求用户清除应用数据。

## 10. 错误、诊断与可观测性

错误信息应包含操作阶段、对象/来源、实际错误及可采取的下一步，不暴露签名私钥、凭据或用户文件内容。示例仅说明合同，具体文案由实现决定：

```text
pkg: dependency conflict: local <package>@<version> requires <constraint>
pkg: local package is managed by the app; upgrade skipped
pkg: package requires unsupported directory symlink; transaction not activated
exec: unsupported ELF interpreter/ABI; detected <details>
runtime: syscall mediation unavailable in this environment; <errno or signal>
```

报告分为：来源/索引可信、归档完整、依赖已满足、文件已安装、配置已完成、程序功能已验证，以及宿主能力已测/未测/拒绝。日志只记录必要元数据；默认不采集命令参数、环境变量、HOME 内容或完整网络地址中的敏感字段。

## 11. 实施顺序与交付门槛

每阶段都保持现有可用功能，先在隔离代次验证，再决定是否成为默认；不得以删除旧实现或清空用户数据代替迁移。

| 阶段 | 主要工作 | 完成门槛 |
| --- | --- | --- |
| 0 基线和接口 | 固定当前真实包、设备、安全域和回归记录；画清当前入口、受限 syscall、代次与来源。定义测试合同和目标元数据。 | 可复现现有已通过/失败场景；明确哪些结果只属于 debug 设备。 |
| 1 本地来源与锁定 | 构建通用清单/本地来源、同一事务求解约束和来源展示；让 PRoot 通过数据驱动安装并附带必要依赖。 | 离线安装、本地版本/字节保护、远程同名及路径覆盖反例通过；不再有 PRoot 名称安装分支。 |
| 2 事务与迁移 | 实现代次记录、失败恢复、并发锁、运行引用与旧状态导入。 | 崩溃注入、升级冲突、用户修改、运行中升级及旧数据保护通过。 |
| 3 通用执行基础 | 抽离公共映射、ABI 识别、exec、库路径及诊断；保留 PRoot 协议适配边界。 | 多个不按名称路由的动态/静态测试程序通过；未知格式和地址冲突正确失败。 |
| 4 文件语义与脚本 | 实测真实链接能力，完成可验证的路径/链接实现；评估脚本约束后端。 | 链接身份及逃逸反例通过；脚本能力未达门槛前默认失败并报告。 |
| 5 syscall 后端原型 | 比较 libc 路径、单一协调器和 PRoot 路线，测线程/子进程/性能及跟踪器冲突。 | 明确每条路线的覆盖范围与失败边界，只有通过真机语义回归才可默认启用。 |
| 6 远程来源泛化 | 将当前 Bun 专用逻辑迁移到声明式远程来源适配器；版本/完整性从可信元数据取得，保留 APK 生态。 | 真机安装、升级、网络/摘要失败和 Bun 功能回归通过，核心不含 Bun 名称分支。 |
| 7 发布验证 | 完整主机、包内容、设备功能和安全域验证；更新许可与现状文档。 | 各项证据可复查，未覆盖能力明确列出；未测 release 不宣称 release 支持。 |

阶段可按依赖关系拆成小改动；阶段 1 的本地保护不应等待全局 syscall 拦截完成。每阶段要有可回退的代次和独立证据，避免未完成的通用后端破坏现有可用路径。

## 12. 验证矩阵

### 12.1 主机与求解测试

- 使用可控的本地模拟仓库和实际包格式，覆盖多版本、架构不符、依赖链、虚拟提供项、冲突、循环、来源不可用、索引变化及无解；求解结果对照所用 APK 版本的真实行为。
- 创建至少两个任意命名的本地包，改变清单内容而不改核心代码即可查询、安装和锁定。安装其他包、移除其他包、`update`、`upgrade`、恢复及修复前后，比较本地已安装版本、来源和逐文件摘要。
- 在新 HAP 清单待迁移或迁移失败时，验证 `pkg` 的移除、重装、修复和升级均不能绕过保护；应用迁移成功后再核对未安装包没有被自动安装。
- 将远程同名更高版本、提供相同虚拟名的包、覆盖相同路径的不同包、ABI 不兼容依赖分别放入仓库，验证不能替换受保护本地包；没有冲突的虚拟提供项按求解规则正常工作。
- 篡改 HAP 清单副本、本地载荷副本、远程索引/归档、摘要和签名；缺公钥、错误架构、归档截断、路径逃逸、重复条目、链接循环/目录链接及资源耗尽均须有反例。不得通过修改预期输出来制造通过。
- 离线安装真正随包且依赖齐全的本地包；离线安装缺依赖包必须报告缺失，不能悄悄联网或声称完整。测试普通远程包仍能查询/安装，证明本地清单不是白名单。
- 脚本和触发器测试包括默认拒绝、显式未配置状态、正确顺序、失败、事务外写入和联网尝试；只有后端可证明其边界时才测试完整执行。
- 事务在每个持久化/切换点注入中断、并发命令、磁盘不足和活动进程；重启后验证旧/新代次之一完整，元数据与文件一致，本地版本未被 `pkg` 更换。

### 12.2 兼容层与设备功能

- 多个独立来源和不同名称的 AArch64 ELF：PIE/非 PIE、动态 musl、适配 glibc、静态程序、脚本和未知格式；验证真实文件的结果、参数、环境、退出码和错误，而非只看 `--version`。其他架构仅在实现并单独验证后列为支持。
- 进程/线程：fork、execve/execveat、spawn、相对路径和文件描述符执行、多线程 exec、信号、等待、标准流、`CLOEXEC`、子进程树与退出回收。分别覆盖 libc 入口和直接 syscall。
- 文件/终端：读写、重命名、文件/硬/符号链接、目录链接、相对路径、`openat`、`readlink`、权限、并发、管道、交互输入、窗口变化、作业信号；真实 PTY 与模拟通道分别报告。
- 系统调用后端：跟踪多线程及 fork/clone/exec，注入信号和中断；测试 PRoot、调试器或程序自身跟踪与协调器同时存在时的行为，测量启动、吞吐、CPU 与内存开销。进入默认前，应先取得现有基线、确定可接受预算并记录结果，不能凭一次跑通决定。
- 真实软件：延续 Bun 的脚本、文件、Worker、子进程、HTTPS、依赖安装，以及 PRoot 的 rootfs 文件、shell、fork/exec、静态程序和 Bun 内嵌场景；再增加不同来源、不同依赖形态的程序。具体程序是回归样本，不是运行白名单。
- 普通用户文件、软件代次和 HOME 在测试前后核对；测试产生的私有临时数据和日志单独记录。无新授权时不自动签名、安装、解锁设备或更改系统设置，遵循[执行纪律](safety.md)。

构建成功、签名包内容正确、覆盖安装成功、真机功能通过分别记录；每条结论包含应用构建、设备、系统版本、安全域、测试输入及日志位置。debug 结果不能推广为 release 结果；同样，一台设备的能力不能推广为所有设备。各阶段未实现的测试应标记待办，不能填写通过。

## 13. 风险与待决问题

| 问题 | 处理原则 |
| --- | --- |
| 宿主限制真实链接、PTY 或执行权限 | 动态探测并保留原始错误；研究通用语义替代，不能伪造支持。 |
| 静态/直接 syscall 与 PRoot 跟踪器冲突 | 先证明单一所有者或可组合方案；不可用时明确失败或只提供已验证范围。 |
| 包脚本的不可回滚副作用 | 无可靠约束时默认不执行、不声称配置完成；事务只保证能够控制的范围。 |
| 本地固定依赖与远程包发生版本冲突 | 求解失败并展示依赖链；由 HAP 更新自带依赖，不能由 `pkg` 强行替换。 |
| 本地包版本更新慢、安全修复滞后 | 显示来源与 HAP 管理状态，通过应用更新交付新构建，不静默降级信任策略。 |
| 额外本地依赖增大 HAP | 记录实际体积，评估私有依赖或共享包方案；不能为了减体积让“离线可安装”变成隐藏联网。 |
| 旧代次来源不完整或用户已修改 | 标记未知、保留原件并阻止自动覆盖；不从包名推断信任。 |
| 单一求解器如何表达本地锁和多来源版本 | 先做 APK 版本与格式兼容原型；语义不完整则保守失败，不引入不一致的第二套求解结果。 |
| 宿主内核或安全域不允许通用拦截 | 保留可用的公共 libc/加载能力，公开覆盖边界；不能据此宣称全部软件可用。 |
